# 会话、会话树与时间线

> 2026-09-24 第二次定稿（v2 每会话一库）。本文档第二节以下的"继承段投影"描述的是 **v1（共享日志+区间）** 模型，已被 v2 取代，保留作设计沿革。v2 的权威描述见第一节。

## 一、v2：一个会话一个 EventStore（现行）

dsh/pi 式物理分账：**会话即日志本身**。

```
<workspace>/sessions/<sessionId>/events.sqlite   本会话全部事件（append-only）
<workspace>/sessions/<sessionId>/header.json     不可变元数据：title/cwd/created_by/
                                                 parent_session_id/fork_at_event_id/kind
<workspace>/sessions/active.json                 活跃会话指针
```

| 操作 | v2 语义 |
|---|---|
| 新对话 | 新建一个会话库（`new_session`，空库幂等守卫） |
| jump / 查看中发消息 | `setActive(sessionId)` —— 切活跃指针，后续追加落回**原文件** |
| rewind（回到此处） | `forkAtFromActive(e)`：≤e 前缀行复制进新库，新库转正；旧库原样保留 |
| fork（从此分叉） | `forkFrom(id, preserveHistory)`：整库复制（无损）或空库；谱系靠 parent 指针，不再携带悬空的 `summary_event_id` |
| 话题切分 `_session_split` | `splitTailFrom(seq)`：尾部（含触发消息）搬进新库，旧库截断 |
| 谱系树 | header 的 parent/forkAt 指针建树（`buildLineageNodes`），零事件扫描 |
| 侧栏 | 读 header（标题落库时写好），按谱系根聚合；scheduled kind 跳过 |

删除的 v1 机制：封口不变量、`end=HEAD` 可变哨兵、悬挂修复（`_repairDanglingHeads`）、
`inherited_ranges` 多段投影、`ThreadScopedStore` 线程打标隔离、侧栏现场探测聚合。
thread 概念退化为 shim（thread_id === sessionId），保留 API 壳兼容 extensions/rpc。

关键代码：`src/core/event-store/session-files.ts`（布局/代理 store/迁移）、
`src/core/projection/session-manager.ts`（v2 换芯）、`src/core/session-listing.ts`（侧栏）。
旧工作区大库在 manager 首次构造时幂等迁移（marker `.migrated-v2`），旧文件保留不删。

## 二、（已废弃的 v1 设计沿革）统一投影模型

> 2026-09-24 第一次定稿。综合 pizza（事件日志 + 全投影 UI）、codex（resume/fork 的"回到那个时刻继续"心智模型）与本项目两级模型的落地设计，解决此前 rewind/跳转语义混乱的问题。

## 一、三层概念（命名统一）

| 层 | 名称 | 是什么 | UI 对应 |
|---|------|--------|---------|
| 1 | **thread（对话）** | 隔离单位，事件按 `thread_id` 打标 | 侧栏一行 = 一整棵分支树 |
| 2 | **session（分支）** | 树节点 = **视面**（事件段的并集） | 分支树上的一个节点 |
| 3 | **event（事件）** | append-only 单线日志里的一行 | 时间线里的一行 |

一个分支的**视面**（你在对话页/时间线里看到的内容、LLM 的上下文）：

```
视面 = 继承段(inherited_ranges) ∪ 主段(event_range)
```

- 每段语义统一为 `(start 不含, end 含端点]`；主段沿用 `(start 不含, end 不含 / HEAD=开)`。
- **单段时代的问题**：分支写成 `(start, HEAD]` 的吞并区间 —— rewind 丢历史、跳回把源封口后同线程其它分支的事件全部串进来。继承段把"带哪段历史"变成**显式声明**，不再靠区间吞并推导。

## 二、各操作的语义（实现与文案的唯一依据）

| 操作 | 入口 | 视面 |
|------|------|------|
| 新对话 | 侧栏「新对话」 | 新 thread，单段 `(ORIGIN, HEAD]` |
| **回到此处（rewind）** | 时间线按钮 / `rewind` RPC / `forkAt` | 封口当前活跃分支；新分支 = `活跃视面截断到 ≤e`（继承段）+ `(SESSION_FORKED, HEAD]`。上下文 = e 及之前的完整历史 + 新消息；**旧尾巴留在旧分支可随时查看** |
| **跳转（jump / 查看中发消息）** | 分支树右键「跳转」 | 封口当前活跃；新分支无损继承目标分支的**完整视面**，同线程其它分支的内容不会被吞并 |
| 查看分支 | 侧栏点击 / 分支树选中 | 只读投影该分支的视面（`get_messages/get_events` 带 `sessionId` 时走 `SessionProjection.getSessionEvents`），不动活跃位 |
| 摘要 fork | `forkFromSession(preserveHistory:false)` / 分支树「从此处分叉」 | 无继承段，仅携带 `summary_event_id` |
| 无损 fork | `--fork` 续写 / `forkFromSession()` | 同 jump，但不做「目标即活跃」no-op 守卫 |

**不变量**：任意时刻同线程只有一个分支 `end=HEAD`（活跃分支）；封口一律封在**边界标记事件**上（`SESSION_CREATED` / `SESSION_FORKED`），绝不封在 `store.head` —— 封在 head 会把最后一条内容事件丢出分支视面。

连续 rewind 天然支持：第二次 rewind 的截断可以落在第一次的继承段里，`inherited_ranges` 数组按日志序拼接。

## 三、UI ↔ 后端联动规则

1. **侧栏一行 = thread**。点击 = 查看该对话的代表分支（线程内最新有内容分支），只读。
2. **分支树 = 目标对话（thread）内部的分支结构**。`history_tree list` 带 `sessionId` 时按目标所属线程取树（GUI 查看历史对话时与对话页看同一段）；不带则取活跃线程。
3. **时间线 = 活跃对话的实时事件流 / 查看目标分支的投影事件**（`get_events` 同一投影规则）。「回到此处」只对活跃对话出现 —— 查看历史对话是只读的。
4. **查看中发消息** = 先无损重开（jump），再把 prompt 发到新活跃分支。

## 四、为什么这样综合

- **pizza**（tomsun28/pizza）：单条不可变事件日志，会话树/时间线/UI 全是日志的投影，任意消息可 fork。本项目同源，采纳其"UI 是投影"原则 —— 查看/时间线/上下文共用 `getSessionEvents()` 一份投影。
- **codex**（OpenAI Codex CLI）：rollout 文件线性追加，resume 即"回到那个会话继续"，无分支树但心智模型极简。采纳其 rewind 语义：**回到 e = 上下文变成 ≤e，之后重新来**。
- **zharness 原有两级模型**（thread 隔离 + session 分支树）保留 —— 它是侧栏/树/隔离的既有骨架，只需把"分支=单段吞并区间"升级为"分支=显式视面"。
