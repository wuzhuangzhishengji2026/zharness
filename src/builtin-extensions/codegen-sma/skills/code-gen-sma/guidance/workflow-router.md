# 复杂度路由 — 判定标准与决策图

> 参考 superpowers `writing-plans` 中"执行方式选择（Subagent-Driven 推荐 / Inline Execution 带 checkpoint）"与
> `dispatching-parallel-agents` 的"独立问题域并行"判定逻辑。本文件定义 code-gen-sma 的复杂度分流规则。

## 一、判定计分表

收到代码任务后，逐项打分（每命中 1 条 +1 分）：

| 维度 | 判定条件（命中 +1 分） |
|------|----------------------|
| 文件规模 | 涉及 >3 个文件（修改或创建） |
| 需求明确度 | 需求模糊、存在歧义、需要与用户多次澄清 |
| 跨模块依赖 | 存在跨模块/跨目录依赖，或改动会影响其他模块 |
| 设计决策 | 需要做架构/接口/技术选型等设计决策 |
| 知识检索 | 需要检索项目知识库或外部资料才能动手 |
| 验证链 | 需要编译、运行、部署、测试等完整验证链 |
| 领域跨度 | 跨越多个领域/技术栈（如同时涉及前端+后端+数据库） |

## 二、判定规则

- **简单任务（0~1 分）** → 推荐 **checkpoint 执行**（`executing-with-checkpoints.md`）
- **复杂任务（≥2 分）** → 再判断子任务独立性，推荐其中一种：
  - 子任务相互独立、数据依赖弱 → 推荐 **子智能体并行**（`subagent-parallel.md`）
  - 子任务强依赖顺序、需要完整质量链 → 推荐 **7 阶段流水线**（`pipeline-guide.md`）
- **推荐仅作建议，最终由用户确认**：向用户说明推荐结果与理由，**等待用户确认或改选**后再执行对应路径；用户未确认前不得开始主体工作。用户明确指定方式时直接按其指定执行（见 SKILL.md 指令优先级）

## 三、决策图

```
代码任务到达
   │
   ├─ 计分 = 0~1（单/少数文件、需求明确、无跨模块、无设计、无检索、无验证链）
   │      └──► 推荐【checkpoint 执行】 列出计划 → 逐任务执行 → 每个 checkpoint 停下确认
   │
   └─ 计分 ≥ 2（多文件 / 需求模糊 / 跨模块 / 设计决策 / 需检索 / 需验证链）
          │
          ├─ 子任务独立（可拆分、无强数据依赖）
          │      └──► 推荐【子智能体并行】 拆分子任务 → 并行派发 → 两级评审 → 集成验证
          │
          └─ 强依赖顺序 / 需要完整质量链
                 └──► 推荐【7 阶段流水线】 理解→检索→分解→实现→编译→部署→汇总
   │
   ▼
向用户说明推荐结果与理由，等待用户确认或改选
   │
   ▼
按用户确认的路径执行（用户明确指定方式时直接按其指定执行）
```

## 四、边界情况

1. **无法判定时**：推荐按复杂任务处理（宁可走完整流程，不可漏掉质量门禁），仍交用户确认
2. **用户明确指定方式**：用户指令优先于本路由（见 SKILL.md 指令优先级），直接按其指定执行，无需推荐
3. **推荐被否时**：按用户改选的方式执行；若用户改选导致流程冲突，说明风险后再继续
4. **中途升级**：checkpoint 执行中发现任务比预期复杂（出现跨模块依赖、需要设计决策），立即停下向用户说明，重新推荐复杂任务路径并交用户确认
5. **中途降级**：流水线/并行路径中若某子任务实际很简单，可直接在当前上下文完成，不必再派发子智能体
