# 阶段五：复核与报告生成

## 1. 漏洞复核与误报排除

对所有发现的漏洞进行二次验证，排除误报。

### 1.1 安全防护检查

| 安全防护 | 说明 | 误报可能 |
|----------|------|----------|
| `snprintf()` 替代 `sprintf()` | 长度限制 | 检查是否使用 `sizeof(buf)` 限制 |
| `strncpy()` / `strlcpy()` | 长度限制 | 检查是否正确处理 null 终止 |
| `fgets()` 替代 `gets()` | 长度限制 | 检查缓冲区大小 |
| `strtol()` 替代 `atoi()` | 错误检查 | 检查是否检查 `errno` |
| `mkstemp()` 替代 `tmpnam()` | 安全临时文件 | 检查文件权限 |
| `realpath()` + 校验 | 路径规范化 | 检查是否校验路径在允许目录内 |
| `execv()` 数组形式 | 参数分离 | 检查参数是否完全可控 |

### 1.2 编译/运行时安全防护

检查是否存在以下安全防护：
```
Grep (在 CMakeLists.txt/Makefile 中):
  -fstack-protector|-fstack-protector-strong
  -D_FORTIFY_SOURCE=2
  -fPIE.*-pie
  -z\s*relro.*-z\s*now
```

如果存在这些防护，某些漏洞可能更难利用，但漏洞本身仍然存在。

### 1.3 不可利用场景

以下情况可标记为误报：
- 输入来自可信源（编译期常量、受信任的内部函数）
- 输入经过了充分的校验（白名单、类型检查、长度检查）
- 代码在 `test/`, `tests/`, `t/`, `*_test.c`, `*_test.cpp` 中
- 代码在 `#if 0` / `#ifdef UNUSED` 块中

## 2. 严重程度判定标准

| 等级 | 条件 | 攻击效果 |
|------|------|----------|
| 致命（Critical） | 远程代码执行/权限提升 | 服务器完全控制 |
| 高危（High） | 信息泄露/认证绕过 | 绕过安全机制 |
| 中危（Medium） | 拒绝服务/资源耗尽 | 服务不可用 |
| 低危（Low） | 信息泄露（低风险） | 有限信息泄露 |
| 信息（Info） | 最佳实践建议 | 无直接风险 |

### 致命（Critical）判定条件:
- 远程命令执行且无认证（RCE）
- 可远程利用的缓冲区溢出（RCE）
- 可远程利用的 Use-After-Free（RCE）
- 可远程利用的格式化字符串（RCE）

### 高危（High）判定条件:
- 本地提权（setuid 程序）
- SQL 注入（可读取敏感数据）
- 认证绕过/越权访问
- TOCTOU 竞态条件（可写文件）
- TLS 证书校验禁用
- 硬编码敏感凭证

### 中危（Medium）判定条件:
- 拒绝服务（资源耗尽）
- 信息泄露（非敏感数据）
- 弱加密（MD5/SHA1/DES/RC4）
- 不安全的临时文件
- 无限制的内存分配（DoS）
- 未初始化变量

### 低危（Low）判定条件:
- 信息泄露（调试信息）
- 不安全的默认配置
- 缺失安全编译选项
- 使用已知 CVE 的 API
- 不安全的信号处理

### 信息（Info）:
- 代码质量建议
- 安全最佳实践建议
- 废弃 API 使用
- 缺少安全头文件
- 已知 CVE 的依赖库（未确认受影响）

## 3. 漏洞报告格式

每个确认的漏洞使用以下格式：

```markdown
### [等级] 漏洞标题

- **严重程度**: Critical / High / Medium / Low / Info
- **漏洞类型**: 缓冲区溢出 / 格式化字符串 / 命令注入 / UAF / 整数溢出 / ...
- **CWE**: CWE-120 / CWE-134 / CWE-190 / CWE-416 / CWE-78 / ...
- **文件**: path/to/file.c:行号
- **函数**: function_name()

**漏洞描述**:
详细描述漏洞成因和影响

**数据流**:
Source: [外部输入来源 recv(sockfd, buf, ...)]
  → [中间处理 parse_request(buf, &req)]
  → Sink: [危险操作 strcpy(local_buf, req.path)]

**修复建议**:
具体的修复方案和代码示例

**验证状态**:
已确认 / 误报 / 待调查，附验证说明
```

## 5. 覆盖率检查

确保所有 `entry_points` 都被审计：

1. 对比侦察结果中的入口点列表
2. 确认每个入口点都被审计
3. 对遗漏的入口点进行补充审计

覆盖率要求：`audited / total_entries >= 95%`
