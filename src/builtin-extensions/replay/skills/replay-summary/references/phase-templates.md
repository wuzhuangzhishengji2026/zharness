# 业务阶段 / 步骤 / 轮次默认模板（可增删改，以实际会话为准）

> 阶段与步骤**不必**照抄：顶部阶段条与左侧步骤由 JSON 动态决定。以下仅为快速起草建议；
> 真实会话里做了什么、分几轮，就写什么。空/无内容的阶段不要放进 `phases`。

## 典型的研发任务四阶段

| 业务阶段 (phases[]) | 建议步骤（普通轮次） |
|---|---|
| 需求分析 requirement | 接收任务 → 检索项目知识 → 分析现有工程 → 提取关键约束 → 人工确认需求 |
| 方案设计 design | 分析现有架构 → 形成实现方案（算法/接口/改动清单）→ 人工确认方案 |
| 开发实现 development | 编写核心算法/代码 → 安全扫描 → 工程编译 → 编译通过 |
| 测试验证 test | 生成测试用例 → 执行真实场景验证 → 分析问题 → 修复后回归 → 测试结论 |

阶段名称/数量可按任务真实形态改，例如：
- 运维/缺陷修复任务：`问题接收 → 问题分析 → 修复验证`
- 数据任务：`数据探查 → 清洗建模 → 结果核验`

## Timeline 轮次：表达返工

顶部业务阶段保持稳定（需求→设计→开发→测试），返工用 Timeline 轮次表达：

```text
run-01 requirement  normal     需求分析（首轮）
run-02 design       normal     方案设计（首轮）
run-03 development  normal     开发实现（首轮：编写算法→编译通过）
run-04 test         normal     测试验证（首轮：生成用例→执行验证→发现3个问题【failed】）
run-05 development  rollback   返回开发修改（transitionMessage「测试发现3个问题，返回开发修改」
                               ——本轮只写：接收测试问题→分析原因→修改代码→重新编译）
run-06 test         reentry    重新进入测试验证（transitionMessage「代码修复完成，重新进入测试验证」
                               ——本轮只写：回归测试→17项全部通过→形成结论）
```

要点：
- 每个 Timeline 轮次**只放本轮实际发生的步骤**，不要重复首轮内容；
- 步骤 `status`：`success`（✓） / `failed`（✕，失败后回放继续） / `confirmed`（人工确认「已确认」）；
- 每轮 `artifacts` ≤3（本轮阶段产出），`metrics` ≤4（本轮数据结果），均随播放刷新；
- 业务阶段耗时 = 该阶段所有轮次真实耗时之和（填在 `phases[].actualDuration`）。
